# Tokenizer Sample-Size 实验方案（第一阶段）

> 日期：2026-09-10 ｜ 状态：**方案待确认，未开跑**
> 目标：只研究「训练 tokenizer 的代表性语料量」对 tokenizer 质量的影响，不训练语言模型。

## 0. 已确认的实测基线（2026-09-10）

### 0.1 训练速度：本地 vs 云端（重要发现）

| 环境 | CPU | 4M 字符 BPE 训练 | 相对速度 |
|---|---|---|---|
| **本地** | Intel Core Ultra 5 225H（14 核，高频 boost 4.9GHz） | **586.9 s（9.78 min）** | **1.0×（更快）** |
| 云端 AutoDL | AMD EPYC 9754 ×2（256 核，Zen 4c 基频 2.25GHz，725GB 内存） | 1795.9 s（29.93 min） | 3.06× 慢 |

**结论**：BPE 训练是**纯单线程 Python 循环**（链表 + lazy heap 顺序合并，无法并行）；
云端 256 核**完全用不上**，单核性能被本地高频消费级 CPU 碾压。
→ **tokenizer 训练应放本地**（云端优势只在 GPU 模型训练）。此前"云端快"的印象来自 GPU 训练，不适用于 CPU 密集任务。

### 0.2 本地 vs 云端结果一致性（交叉验证）

同一 4M 样本，两边训练出的 tokenizer **逐位一致**（chars/token、vocab 利用率、
top100 覆盖、熵、round-trip 全部相同）→ **抽样与训练完全可复现，CPU 差异只影响速度**。

## 1. 固定不变的部分（严格遵守）

- byte-level BPE 实现、`PRETOK_RE = \w+|[^\w\s]|\s+`、`vocab_size=6144`
- special tokens：`<unk>`(0) / `<eos>`(1)，`NUM_SPECIAL=2`
- 训练后端 `fast`、tie/merge 顺序（与 legacy 同序，有等价性测试保证）
- 抽样逻辑与 `train.py` 完全一致：**100 段均匀撒**（每段 `N/100` 字符，间隔 `len(corpus)/100`）
  ⚠️ 不截取前 N 字符
- 语料：`data/train_webnovel_v2.txt`（3.5GB / 12.4 亿字符）完整文件

## 3. Held-out benchmark（不参与 tokenizer 训练，一次生成后冻结）

**来源**：`data/val_webnovel_v2.txt`（405MB，训练语料之外，天然 held-out）

**构成**（固定 seed 抽取，生成后存盘冻结，4 个 tokenizer 共用）：
- **B1 全书级**：随机 20 本小说，每本取前 20K 字符（测跨书差异）
- **B2 均匀级**：全 val 均匀撒 200 段 × 2K 字符 = 400K 字符（测整体压缩率）
- **B3 边界级**：含特殊字符/emoji/罕见字的 5K 字符片段（测 round-trip 边界）
- 合计约 **805K 字符**，编码量小（每组评测秒级）

## 4. 评测指标（4 个 tokenizer 统一测）

| 指标 | 定义 | 预期回答 |
|---|---|---|
| tokens/char | Σtokens / Σchars | 样本量↑ 是否带来更好压缩 |
| chars/token | Σchars / Σtokens | 同上（直观） |
| bytes/token | Σbytes / Σtokens | 跨语言可比口径 |
| 总 token 数 | B1/B2/B3 各算 | 同语料训练成本 |
| vocab 利用率 | 被使用的 vocab 条目 / 6144 | 样本量↑ 是否激活更多 token |
| token 频率分布 | top-100 覆盖率、熵、Zipf 斜率 | 分布是否更均衡 |
| 不同小说压缩率 | B1 每本 chars/token 的均值±标准差 | 跨书泛化性 |
| encode 速度 | chars/s（含预分词） | 推理成本 |
| decode 速度 | tokens/s | 同上 |
| round-trip 正确性 | decode(encode(x)) == x 比例 | 必须 100% |

| 对比 | token 节省 | 相对提升 | 训练成本倍数 |
|---|---|---|---|
| 4M → 8M | −620 | **+0.193%** | 2.09× |

### 8.3 分书泛化（B1 20 本 chars/token 的 mean ± std）

| sample | mean | std | min | max |
|---|---|---|---|---|
| 4M | 1.2370 | 0.0551 | 1.1422 | 1.3454 |
| 8M | 1.2383 | 0.0540 | 1.1483 | 1.3420 |
| 16M | 1.2425 | 0.0547 | 1.1466 | 1.3480 |
| 32M | 1.2444 | **0.0564** | 1.1488 | 1.3642 |

→ 跨书一致性**没有改善**（32M 的 std 反而略大）。样本量增加主要提升"均值"，不改善"跨书稳定性"。

### 8.4 vocab 利用（6144 中实际用到）

| sample | 用到 | 未用 | 利用率 |
|---|---|---|---|
| 4M | 5446 | 698 | 88.64% |
| 8M | 5492 | 652 | 89.39% |
| 16M | 5540 | 604 | 90.17% |
| 32M | 5582 | **562** | 90.85% |

→ 即使 32M 样本，仍有 **562 个 token（9.15%）几乎不被使用**（held-out 集上）。

### 8.5 结论

1. **收益递减明确**：样本量从 4M 增到 32M（**8 倍**、训练时间 **9.4 倍**），
   压缩率只提升 **0.623%**（chars/token 1.2429 → 1.2507）。**性价比极低。**
2. **4M 已是合理工作点**：当前生产 baseline（4M）与 32M 的差距 <0.7%，
   而 8M 仅比 4M 好 0.19% —— **不值得为这点收益付出 2-9 倍训练成本**。
3. **速度无显著变化**（encode ~1850k chars/s、decode ~7700k tokens/s 全档位一致）；
   **round-trip 全部 100% 通过**（4 个 tokenizer 均无编码-解码损失）。
4. **分书泛化不随样本量改善**（std 无下降趋势）——样本量提升的是"整体压缩均值"。
5. **对第二阶段的启示**：4M 下仍有 698 个 vocab token（11.4%）未被使用，
   32M 也剩 562 个（9.2%）→ **vocab_size=6144 可能偏大**，
   值得进入第二阶段消融（4096/6144/8192/12288）验证是否有冗余。

### 8.6 建议

- **维持 tokenizer 训练样本 = 4M**（不因样本量再增大而额外投入）
- **第二阶段（vocab_size 消融）有充分理由开展**：候选 4096 / 6144 / 8192 / 12288，
  固定 sample=4M，复用同一 held-out benchmark 与评测脚本
- 若第二阶段也显示收益有限，则 tokenizer 侧优化到此为止，把精力放回数据/模型 scaling

## 10. 第二阶段：vocab_size 消融（已完成）

### 10.1 实验设置

| 项 | 设定 |
|---|---|
| 训练样本 | **固定 4M 字符 = 3,995,977**（与阶段一逐位同一份样本，严格单变量） |
| vocab 候选 | 4096 / 6144 / 8192（按指示**取消 12288**） |
| 其他 | 字节级 BPE、`PRETOK_RE`、special token、全部算法与阶段一一字未改 |
| 评测 | 复用同一 held-out benchmark（`tok_bench/`，未参与任何 tokenizer 训练） |

**关于只训练 1 个 tokenizer 的说明（方法要点）**

BPE 是顺序贪心合并，第 k 个 merge 的 id = `len(vocab)`（258 起连续分配），
因此**大词表 tokenizer 截断后与独立训练的小词表 tokenizer 逐位等价**（前缀性质）。
本阶段只需独立训练 vocab=8192（722.7s），再截取派生 4096 / 6144：

- `tok_v8192.pkl`：独立训练（7934 merges）
- `tok_v6144_from8192.pkl`：截取（5886 merges）→ 与阶段一**独立训练**的 `tok_4M.pkl` 对比
  → **✅ 完全一致**（逐位相同），前缀性质在本语料/本实现上验证通过
- `tok_v4096_from8192.pkl`：截取（3838 merges）

好处：彻底排除"3 次独立训练各自的合并路径随机差异"，三档唯一变量就是 vocab 大小。

### 10.3 长尾分析（决定性问题）

阶段一在小 benchmark（400K 字符）上看到"6144 有 11.4% token 未被使用"，
但那可能是**小样本假象**。为此在 held-out 的 `val_webnovel_v2.txt` 上按同样方式
**分层均匀采样 40M 字符**，统计词频并按 **1B token 训练预算**外推每个 token 的梯度更新次数。

| vocab | 用到 | 未用 | 利用率 | 中位出现次数 | 预计 <1000 次 | 预计 <10000 次 |
|---|---|---|---|---|---|---|
| 4096 | 3871 | 225 | **94.5%** | 106,391 | 70 (1.7%) | 173 (4.2%) |
| 6144 | 5720 | 424 | 93.1% | 66,299 | 137 (2.2%) | 367 (6.0%) |
| 8192 | 7470 | 722 | 91.2% | 46,112 | 237 (2.9%) | 704 (8.6%) |

- 预计出现 **<100 次**的 token：22 / 39 / 70 个，且它们占用的训练 token 槽位 ≈ **0.00%**
- 即使 vocab=8192，也只有 2.9% 的 token 会低于 1000 次更新 → **长尾不足以否决 8192**

### 10.4 结论

1. **4096 淘汰。** 相对 6144 压缩率损失 6.17%，只换来 2.30% 的参数节省 —— 明显不划算。
   利用率虽最高（94.5%），但"利用率高"只是"词表小"的同义反复，不代表模型更好。
2. **更正阶段一的判断。** "6144 词表偏大、11.4% 冗余"是 400K 字符小样本造成的假象；
   40M 字符下 6144 仅 424 个未用（6.9%）。**"vocab 偏大"的证据比原先估计的弱得多。**
3. **6144 → 8192 收益递减但方向仍为正**：再省 3.44% token（第一档的 52.3%），
   代价同为 +2.30% 参数。固定 1B token 预算下，8192 相当于**多看 3.56% 的文本**
   （chars/token 1.2429 → 1.2872），且 512 上下文覆盖的字符数同样 +3.56%
   —— 压缩侧的收益是真实的。
4. **速度与正确性无差异**：encode ~1800k chars/s、decode ~7700k tokens/s 三档一致；
   round-trip 全部 100%。
5. **但 intrinsic 指标已经到极限**：6144 vs 8192 的差距（3.44% token / 2.30% 参数）
   无法仅靠 tokenizer 侧指标裁定，剩下的只有 LM 训练能回答。

### 10.5 建议

- **继续现有 v3 线（要与 v3_alpha 3.2097 等历史结果可比）→ 保持 vocab=6144 不动。**
  换词表会让所有历史结果失去可比性，而预期收益只有 3% 量级。
- **若开新线** → 8192 是纯指标最优（同 token 预算多看 3.56% 文本、上下文覆盖更大），
  代价是 +2.30% 参数与 +33% 输出层宽度（后者使单步 FLOPs 约 +2%）。
- **4096 在任何情况下都不推荐。**
- 最终裁定需要**一次极短 LM 对照**：固定算力、固定同一段文本、
  **比较 bits/char（而非 per-token loss）**——不同 vocab 的 per-token loss 不可直接比较，
  这是本阶段唯一未被覆盖的部分，需要占用云端 GPU。
