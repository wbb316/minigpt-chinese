## 结论摘要

**流式可行，框架层零障碍（已实测通过）。** 真正的坑有两个：

1. **增量解码（必须做）** —— 不做会**静默改字**，不只是乱码
2. **满窗每步重建（预存在的性能悬崖）** —— 文档里低估了，会被流式放大成肉眼卡顿

---

## Q1 增量解码（最大坑，必须做）

- `decode` 实现：`data/tokenizer.py:313-323`，核心
  `b''.join(parts).decode('utf-8', errors='replace')`（:323）→ **是 bytes.decode**，
  用 `errors='replace'`。特殊 token 走 :317-318 被替换成字面量 `<unk>`/`<eos>`
  （`EOS_ID=1`、`UNK_ID=0`，:31-32）
- 字节接口：**有** —— `tok.vocab` 就是 `{id: bytes}`（:57/:60-61/:156），
  无 `encode_bytes`/`decode_bytes` 封装（`dir()` 实测无）。不需要 HF `tokenizers`
- **★ 实测（关键）**：词表 8192 个 token 里 **458 个单独不是合法 UTF-8**；
  真实生成里 partial token 占比 **7.0%~10%**（16/200、14/200、12/120、6/120、2/120；
  合计 46/600 = **7.67%**）
- 最小复现：`tok.encode('龘')==[779,154]`，`tok.decode([779])=='\ufffd'`；
  `'𠮷'→[242,162,176,185]`，4 个 token 各自解出 `�`，拼起来才是 `'𠮷'`
- **★ 后果不只是乱码，是静默改字**：真实序列整体 decode 263 字符、0 个 U+FFFD；
  naive 逐 token 拼接产生 **16 个 U+FFFD**，且在 char36 处 `'王嫣'` 变成 `'王��'`
  （`'…王��笑嘻嘻'` vs `'…王嫣笑嘻嘻'`）

### 可行方案（实测等价）

```python
dec = codecs.getincrementaldecoder('utf-8')(errors='replace')
# 每步：dec.decode(tok.vocab[nid], final=False)
# 收尾：dec.decode(b'', final=True)
```

在真实生成序列（含 7~8% partial token、跨 48 次超窗重建）上
**增量 == 整体 decode，U+FFFD = 0**。
手写"只输出完整 UTF-8 前缀"也等价，但 `codecs` 版更短更稳。

**对现有 decode 零改动**：新增**独立**增量解码器（放 `app/` 流式层或 tokenizer 新增方法），
**不要**把 `decode` 改成有状态。

### 特殊 token

`EOS_ID=1` 今天会被 decode 成字面量字符串 `"<eos>"`（tokenizer.py:317-318）——
流式里应**遇到 0/1 就停止/跳过，不喂解码器**。
实测 600+ 生成 token 里 0 次特殊 token；`train/train.py:568` 明确写
`eos_token: <eos> (id=1) [纯续写训练未用]`，全仓库无任何地方写入 EOS。
→ 属**廉价防御**，非硬需求。

### 附带的同类坑：`clean_text()` 不能逐帧调用

`app/server.py:21-30` 的 `html.unescape`：
- 整体 `'&#8943;'` → `'⋯'`
- 按字节边界拆成 `['&#89','43;']` 分帧调用 → **`'Y43;'`**（`&#89` 被解成 `'Y'`）

实测 1082 个生成字符里 `'&'` 出现 **0** 次，实际概率极低。
低成本做法：保留累积原文、对"整体 clean 后的文本"取 diff，
并把尾部可能的半截实体（`&` 后无 `;`）hold-back 几帧。

## Q2 超窗重建：预存在的性能悬崖（比文档严重）

- 代码：`model/generation.py:47-52`。
  注意条件 `cache_len + 1 > block_size`：**一旦缓存到 512，之后每一步都进重建分支**
  （重建后 cache_len 仍是 512）
- **★ 实测（prompt 300 token + 生成 260）**：
  - 第 212 步首次重建，**重建 48 次 = 之后每一步都重建**
  - 重建步 **506~893 ms（mean 675 ms）** vs 常规步 **40.3 ms** → **16.7×**
  - 总耗时 **40.96 s**；若不重建理论只需 **10.48 s**
- **已吐出的文本不受影响**：重建只换模型 KV/窗口，`ctx`（含全部历史）不变，
  decode 用的是 `ctx` → 流式里**绝不能**因为重建而 reset/重发解码缓冲
- 流式注意：重建期间 0.5~0.9s 没有新 token → 用户看到"卡住"。可选发 SSE 心跳注释帧
- ⚠️ **前端「接着写」会把全文塞回输入框**（`index.html:1303-1334`）→ prompt 必然被
  `generation.py:33` 截到 512 → **从第 1 步起就每步重建**（30 token 也要 ~20s）。
  流式会让这个现象**第一次变得肉眼可见**

## Q3 FastAPI 侧最小改法

### `generate_ids` 调用方（全仓库 grep）

| 位置 | 用法 |
|---|---|
| `app/server.py:18,239` | **唯一真实调用** |
| `scratch/compare_generation.py:22,68-71` | `ctx, _ = generate_ids(...)`，**依赖签名** |
| `generate.py:27` | import 但**未使用** |
| `scratch/verify_v3_load.py:45` | import 未使用 |

→ **可以不改签名**，新增 `stream_ids()`；建议把 `generate_ids` 改成
`new = list(stream_ids(...))` 的薄封装（签名/返回值/history 不变），
避免两处采样循环漂移（`sampling.py` 开头 docstring 就在强调这点）。
rng 顺序不变 → 同 seed 结果应**逐位一致**（需一条等价测试）。

### media type

三种实测都通。**推荐 SSE**（`text/event-stream; charset=utf-8`）——
因为要带尾部元数据（`elapsed_ms`/`new_tokens`），纯文本 chunked 得自己发明分帧。

| 方案 | 实测 |
|---|---|
| FastAPI 0.136 原生 SSE（`response_class=EventSourceResponse` + 同步生成器） | 自动成帧 `data: {...}\n\n`（fastapi/routing.py:61-67, 496-532；同步生成器同样走 `iterate_in_threadpool`） |
| 手写 SSE 帧 + `StreamingResponse(gen(), media_type='text/event-stream')` | 通 |
| NDJSON（`application/x-ndjson`，每行一个 JSON） | 通，前端 parse 最省事 |

三者都：POST 可用、`Transfer-Encoding: chunked`、无缓冲、逐帧到达
（150ms 间隔实测严格 150ms）。

### ★ 同步 def 生成器 + StreamingResponse：**可以，不需要 async def**

- `starlette/responses.py:230-233` 对非 AsyncIterable 自动 `iterate_in_threadpool(content)`
- `starlette/concurrency.py:39-57` 每次 `next()` 用 `anyio.to_thread.run_sync` 跑在工作线程
- **实测**：流式进行中并发 `/health` 延迟 **4.2 ms**（事件循环没被堵）
- ⚠️ **绝不要 `async def` 里直接调 `sample()`** —— 会阻塞事件循环

**线程池上限**：anyio 默认 40（`anyio/_backends/_asyncio.py:2957`）。
今天 `/generate` 整段生成占 1 个槽 20s；流式只在每步的 26ms 占槽，**反而更宽松**。
uvicorn 报 ASGI `spec_version=2.3`（< 2.4）→ starlette 走
`responses.py:268-277` 的 `listen_for_disconnect` + cancel scope 路径。

### ★ 建议新增 `POST /generate/stream`，**不要改造 `/generate`**

`README.md:207-209` 把 `/generate` 的字段当契约写着；
前端 `index.html:1468` 也有"不改 /generate 字段"的注释。

## Q4 前端改动（评估）

- 现状：`await response.text()` 在 `index.html:1176`；错误分支 1180-1187 需
  "**先判 `response.ok`，非 2xx 仍用 `response.text()` 读 JSON detail**"，
  2xx 才走 `body.getReader()` + `new TextDecoder('utf-8')`（配 `{stream:true}`
  处理跨 chunk 多字节）
- **AbortController 兼容，但语义变了**：
  - 现有：1050-1052 局部 controller、1092-1095 `abortGenerate`、1256-1259 catch、
    1267-1283 finally（`inflight === myRequest` 守卫）
  - **★ 同构探针实测：客户端断开后服务端同步生成器在 1 步内就停了**
    （日志 5/20 步，之后不再推进）
  - 所以 **644-650 的「停止等待」文案、1054-1064 那段"不做流式/服务端不会停"的注释、
    1259 的 toast 都要改**；按钮可正名为「停止生成」
  - `restoreAfterAbort()`（1075-1089）会回退到上一次结果 —— 流式下**已渲染的半截文字
    不该消失**，应改为"保留已生成部分 + 结束收尾"
  - `lastResult`(1190) / `pushHistory`(1243-1246) / `updateContinueBtn`(1247)
    必须挪到"**流结束**"事件之后
- **渲染函数**：`toParagraphs`(824-831) + `fillArticle`(832-846) 是**幂等的全文重渲染**，
  流式下可每帧重调（正确性没问题，最终 DOM 与今天一致）。两个代价：
  - (a) 每帧清空+重建全部 `<p>`，破坏选区并引发重排 → 建议 **60–100ms 节流或 rAF**
  - (b) `toParagraphs` 规则会**回溯改段落**：`'A\nB'→['A','B']`，但追加空行后
    `'A\nB\n\nC'→['A\nB','C']` —— 先前渲染成两个 `<p>` 的会被合并
    （单换行在 `<p>` 里塌成空格）。逐字符模拟 108 字样本：103/108 步最后一段在变
    （正常），合并事件在该样本里 0 次（空行出现得早），机制本身由 4 组输入实测确认
  - **不需要重构**：加一个流式专用渲染路径（累积全文 + 节流 + 只在 `\n\n` 边界重切）
    约 **30 行**

## Q5 性能：流式几乎免费，瓶颈仍是模型本身

- 每 token 模型步：mean **25.8~27.2 ms**，p50 25.7，min 19.9，max 48.0
  （与 60=1.38s / 150=3.47s / 300=7.52s 完全吻合）
- **增量解码开销：0.29 µs/token**（对比 naive 每步 decode 前缀 10.4 µs、
  每步 decode 全文 18.9 µs）→ 相对 26ms/步是 **0.001%**
- 分块网络/ASGI 开销：`/stream` 相邻块间隔减掉 sleep 后 **0.63~1.1 ms/块**；
  512 个极小 chunk 连发 61.5/80.2ms ≈ **0.12~0.16 ms/块**；同 body 一次性返回 1.4~2.1ms
  → 相对 26ms/token **≲4%**
- **★ 首字延迟 = prefill（实测）**：512→**482ms**、256→259ms、128→137ms、64→104ms、16→66ms
  （短 prompt 首 token 26~44ms）→ 今天 512 token 要等 **19.5s**，流式 **~0.5s 出第一个字**
- 唯一会变慢：满窗后每步重建（Q2，675ms/步）；并发多路流在 GIL 下互相拖慢（未测）

## 推荐实现方案

### 必做

1. `model/generation.py` 新增 `stream_ids()`（生成器，yield int），
   `generate_ids` 改为其薄封装（**签名不变**）+ **同 seed 等价测试**
2. 新增增量解码器：`codecs.getincrementaldecoder('utf-8')('replace')` 喂 `tok.vocab[nid]`；
   id∈{0,1} 停止/跳过；只在 non-empty 时产帧。**不改 `BPETokenizer.decode`/`encode`**
3. `app/server.py` 新增 `POST /generate/stream`（**同步 `def`** + `StreamingResponse`，SSE）：
   `data: {"delta": ...}` … 最后 `event: done, data: {"elapsed_ms","new_tokens"}`；
   首个 delta 含 prompt（保持"全文"语义，前端 `fillArticle(累积文本)` 最终 DOM 与今天一致）；
   **不写 `async def`**。保留 `/generate` 原样
4. 前端：非 2xx 走旧 `response.text()` 错误路径；2xx 走 `getReader()`+`TextDecoder({stream:true})`，
   按 `\n\n` 分帧；累积全文 + 节流渲染；`done` 后才写 meta/lastResult/pushHistory/updateContinueBtn

### 可选

5. `clean_text` 尾部实体 hold-back（实测 1082 字 0 个 `&`，可延后）
6. 文案/注释更新 + abort 保留半截文本
7. SSE 心跳帧
8. 单独评估是否修 Q2 重建悬崖（**不是流式的一部分**）
