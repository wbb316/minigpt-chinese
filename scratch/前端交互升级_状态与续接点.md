## ★ 已定方案：**方案 A（轻量/无状态）** —— 用户已确认选 A

| 交互 | 方案 A 的实现 |
|---|---|
| 流式生成 | 后端新增流式端点（逐步吐 token）；前端 `response.body.getReader()` 逐段渲染 |
| 停止 | 后端加 `threading.Event` 取消标志，在**下一个 token 边界**退出；前端断流 |
| **继续** | **不保服务端状态**：把已生成文本接回 prompt，**重新发一次请求**，靠既有 `prompt[-block_size:]` 滑动窗口保连贯 |
| 重新生成 | 丢弃本次，从原 prompt 重发 |

### 为什么选 A（当时给用户的理由，供复查）

1. 「继续」体验差别很小 —— prefill 512 token 在 CPU 上约 1s，而生成 100 token 要 3s，
   用户多等 1s 几乎无感
2. 连贯性 A 也不差 —— 重发时 prompt 含全部已生成文本，模型能看到完整尾部
3. **B 的内存风险真实**：方案 B（服务端持 KV cache 会话）每会话几十 MB，
   泄漏或不淘汰会吃掉几 GB，而收益只是省 1s
4. A 的代码可被 B 复用 —— 流式与停止的实现相同，将来若要 B 只需再加会话层

### 何时该改成方案 B

只有当用户要「连续继续很多次」（例如每 50 字停一次、继续 20 次），
A 的每次 prefill 累积成可观开销时才值得。那时的增量：
会话管理器（TTL + 上限 + 线程安全）+ `generate_ids` 重构成可步进（cache 跨请求存活）。

## 流式的两个已知大坑（★ 详见完整调查报告）

> **完整报告：`scratch/流式输出_技术调查报告.md`**（含全部实测数据、代码行号、
> 推荐实现方案、工作量估计）。**开工前必读**，这里只摘结论。

1. **增量解码（必须做）** —— 词表 8192 个 token 里 **458 个单独不是合法 UTF-8**；
   真实生成里 partial token 占 **7.67%**（46/600 实测）。
   逐 token 独立 decode 的后果**不只是乱码，是静默改字**：
   实测某序列整体 decode 263 字符 0 个 U+FFFD，naive 逐 token 拼接产生 16 个，
   且 `'王嫣'` 被改成 `'王��'`。
   **方案**：`codecs.getincrementaldecoder('utf-8')(errors='replace')`，
   每步喂 `tok.vocab[nid]`（实测与整体 decode 逐字等价，U+FFFD=0）。
   **不改** `BPETokenizer.decode`（新增独立增量解码器）。
   附带的同类坑：`app/server.py:21-30` 的 `clean_text()` **不能逐帧调用**
   （`'&#8943;'` 分帧会变成 `'Y43;'`）
2. **同步生成器 vs `async def`** —— **实测已确认**：Starlette 对同步生成器
   自动跑进线程池（`responses.py:230-233` + `concurrency.py:39-57`），
   流式进行中并发 `/health` 延迟仅 **4.2 ms**。
   → 用**同步 `def` 生成器 + `StreamingResponse`** 即可，
   ⚠️ **绝不要 `async def` 里直接调 `sample()`**（会阻塞事件循环）。

### ★ 第 3 个坑：满窗每步重建（调查报告新发现，比文档严重）

`model/generation.py:47-52` 的条件是 `cache_len + 1 > block_size` ——
**一旦缓存到 512，之后每一步都进重建分支**。实测（prompt 300 + 生成 260）：

- 第 212 步首次重建，之后**重建 48 次 = 每一步都重建**
- 重建步 **675 ms（506~893ms）** vs 常规步 **40.3 ms** → **16.7×**
- 总耗时 **40.96 s**，若不重建理论只需 **10.48 s**

#### ★★ 这个悬崖会让「接着写」在长文本上不可用（已实测确认）

「接着写」把上一轮**全文**塞回 prompt → prompt 必然 ≥512 →
`generation.py:33` 截到尾部后**仍正好是 512** → 从第 1 步起**每一步都重建**。

实测（`prompt = 一句话 × 50 ≈ 800 字`，`max_tokens=300`）：**HTTP 请求 120 秒未返回**
（对比：短 prompt 下 300 token 只需 7.5s）。

**即：内容越长，「接着写」越慢，且是每步 675ms 的固定重罚 —— 不是可接受的体验。**
这是**预存在问题的暴露**（流式/接着写之前没人会碰到满窗），但用户一定会碰到。

→ **修复方向**（属于独立立项，不属于流式）：
滑动窗口时**不需要每步重算整段 KV**。典型做法是维护一个会滚动的 cache ——
新 token 追加、超长时丢弃最旧的若干（而不是把 512 个 token 重新 prefill 一遍）。
代价：`model/generation.py` 的窗口逻辑要改写 + 与 RoPE 的位置偏移正确对齐
（丢最旧后位置索引要重锚）。**建议在流式之前或之后单独评估，别混在一起做。**

已吐出的文本**不受影响**（重建只换模型 KV，`ctx` 不变，decode 用的是 `ctx`）→
流式里**绝不能**因重建而 reset 解码缓冲。

### 其它关键结论

- 建议**新增 `POST /generate/stream`**，不要改造 `/generate`
  （`README.md:207-209` 把它的字段当契约；前端也有"不改字段"的注释）
- `generate_ids` 有调用方依赖签名（`scratch/compare_generation.py`）→
  新增 `stream_ids()`，`generate_ids` 改为其薄封装 + **同 seed 等价测试**
- 推荐 **SSE**（要带尾部元数据 `elapsed_ms`/`new_tokens`）
- **首字延迟 = prefill**：512 token → **482ms**（今天要等 19.5s 才见第一字）
- 流式额外开销：增量解码 **0.29 µs/token**、分块网络 **≲4%** → **几乎免费**
- ⚠️ 流式下**停止的语义会变**：实测客户端断开后服务端生成器**在 1 步内就停**，
  所以「停止等待」文案与"服务端不会停"的注释**都要改**，按钮可正名为「停止生成」
