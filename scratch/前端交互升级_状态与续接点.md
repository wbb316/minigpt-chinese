## ★ 已定方案：**方案 A（轻量/无状态）**

| 交互 | 方案 A 的实现 |
|---|---|
| 流式生成 | `POST /generate/stream`（SSE）逐 token 吐；前端 `getReader()` + 节流重绘 |
| 停止 | **不需要服务端取消机制**：客户端 abort → TCP 断开 → starlette 不再 `next()` 生成器 → 剩余步数不执行 |
| **继续** | 不保服务端状态：把已生成文本接回 prompt **重新发一次请求**，靠 `prompt[-block_size:]` 滑动窗口保连贯 |
| 重新生成 | 丢弃本次，从原 prompt 重发 |

### 为什么选 A

1. 「继续」体验差别很小 —— 重发只是多一次 prefill（512 token ≈ 0.48s），用户几乎无感
2. **B 的内存风险真实**：每会话几十 MB KV cache，泄漏/不淘汰会吃几 GB，收益只是省 0.5s
3. A 的实现可被 B 复用 —— 将来要 B 只需再加会话层

### 何时该改成方案 B

只有当用户要「连续继续很多次」（每 50 字停一次、继续 20 次），prefill 累积成可观开销时才值得。

### 三个必须知道的坑（都已在代码里堵住）

1. **增量解码（必须）** —— 词表 8192 里 **458 个 token 单独不是合法 UTF-8**。
   逐 token 独立 decode **不只是乱码，是静默改字**：
   实测整体 decode `'李美怡是谢尔盖的女儿'`（167 字符 0 个 U+FFFD），
   naive 逐 token 拼成 `'李美??是谢尔盖的女儿'`（170 字符 6 个 U+FFFD，首个分歧在 char38）
   —— **`怡` 字被吃掉**。
   → 用 `codecs.getincrementaldecoder('utf-8')(errors='replace')`，
   每步喂 `tok.vocab[nid]`。**不要改 `BPETokenizer.decode`**（已有测试依赖其语义）。
2. **`clean_text()` 不能逐帧调用** —— `html.unescape('&#8943;')` 整体是 `'⋯'`，
   按边界拆成 `['&#89','43;']` 分帧会解成 `'Y43;'`。
   → `_hold_back_incomplete_entity()` 把尾部半截实体扣到下一帧。
3. **`stream_ids` 只 yield 新 token，不含 prompt** ——
   而 `/generate` 的 `text` 是**全文**（prompt + 新生成）。
   漏掉 `itertools.chain(ids, counted())` 这一步 → 流式全文没有开头，
   前端 `startsWith(prompt)` 立刻失效。**这个 bug 真实发生过，被 e2e 对拍抓住。**

### ★ abort 语义（实测结论，别再传错）

**真的会停，而且一步都不多算。** 判据是 **CPU**，不是日志：

| 测量 | 结果 |
|---|---|
| 中止后 300s 内进程 CPU 增量 | **0.3%**（纯空转噪声） |
| 服务端 `已算` token 数 | **恰好等于**客户端已消费的 token 数 |
| 内存（10 次连续中止） | +13.6 MB 后**持平**（前 5 次爬升，后 5 次 0 增长）→ 有界，非无界泄漏 |

⚠️ **两个流传过但站不住的说法，别再引用**：

- ❌「断流后服务端还会多算几十步（~84 token）」——
  那是 **Python 客户端没真正关掉 socket** 的假象（`requests.post` 模块级调用每次都新建
  Session，Session 被 GC 时才关 TCP；连接还活着，服务端当然继续算）。
  **浏览器 `AbortController` 会立刻断开。**
- ❌「`[stream] 提前结束` 日志能证明停了」——
  starlette 只是**不再 `next()`** 生成器，**并不保证马上 `close()`** 它。
  实测收尾日志 **2.8s ~ 266s** 才打；**300s 静默期内甚至从未执行**。
  日志是观测手段，不是判据。

→ 若将来真要「中止即释放」，需要显式关闭生成器（`itertools`/`StreamingResponse` 层面），
  目前判断**不值得做**（CPU 已经是 0，内存有界）。

## ★ 另一条独立改动：满窗每步重建（「悬崖」）

`generation.py` 原条件 `cache_len + 1 > block_size` → 缓存到 512 后**每一步都重建**。

### 修复：`max_overrun`（默认 **64**）+ 原地扩 RoPE 表

50M v3 / prompt 正好 512 / 40 token，3 次取中位：

| `max_overrun` | ms/token | 质量 |
|---|---|---|
| 0（修复前语义） | 269.3 | 连贯 |
| 16 | 50.4 | 连贯 |
| 32 | 40.0 | 连贯 |
| **64（默认）** | **35.7** | **连贯** |
| 128 | 36.9 | ~60 token 后词沙拉 |
| 256 | 39.1 | 明显退化 |

- **150M 真实权重 / 848 token prompt：689.3 → 41.8 ms/token = 16.5×**
- **`max_overrun=0` 与修复前逐位一致**（3 checkpoint × 6 prompt 长度 × 40 token，ctx 与 new_ids 全同）
- 默认 64 是**速度峰值**，且 128/256 又慢又退化 —— 不要"顺手调大"
- RoPE 表**原地扩展**（cos/sin 是持久 buffer；重建长表会让 `load_state_dict(strict=True)` 因 shape 不符失败）
- 副作用：扩表后**不要**在同一个 gpt 对象上再 `load_state_dict(strict=True)`

★ **P0 是唯一一个真 bug**（其余是体验/措辞），根因值得记住：
`hidden` 只靠浏览器默认样式表 `[hidden]{display:none}` 生效，而**作者样式优先于默认样式、
与特异度无关** —— 所以 `.row{display:flex}` 能直接让 `class="row" hidden` 可见。
JS 侧（`setHidden` 用 setAttribute）**一直是对的**，是被 CSS 反杀的。
**新加任何带 `display` 的 class，都要想到它可能压掉某个 `hidden`。**

### 本轮刻意**没做**的（留给后续判断）

- **`.controls` 是 sticky 且比视口高** —— 吸附后底部（历史记录、最后一个滑块）
  在屏外，要滚到页面最底才够得到。修法是在 `@media (min-width: 1024px)` 里给
  `.controls` 加 `max-height: calc(100vh - 48px); overflow-y: auto`，
  代价是左栏出现**内层滚动条**（滚动会先滚左栏再滚页面，可能更烦）。
  因为 P1 已把主按钮移到顶部，残余影响很小，**故意留着没做**，等用户反馈。
- 字数接近 2000 上限时没有提示
- 滑块缺 `aria-describedby` 关联提示文字（读屏只念到数值，念不到"越低越保守"）
